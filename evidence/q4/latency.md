# Q4 latency: audio received to nudge on the agent's screen

Generated by `npm run q4` on 2026-10-02: 5 recordings replayed at 1x real-time speed in 250 ms chunks, concurrently, through the HTTP server and a WebSocket client on the same machine. 16 nudges delivered, 72 transcript segments.

Percentiles are nearest-rank over delivered nudges. Server and client share a clock (same host), so cross-process differences are valid here; across machines they would need clock sync.

| End to end | 16 | 2 ms | 5 ms | 5 ms | audio received -> nudge received by the client |

## Per-chunk transcription

Transcript segments emitted: 72. With the simulated recogniser, a final segment is released on the first 250 ms chunk at or after the turn's end, so the audio-side wait is between 0 and 250 ms by construction and is not a measurement of recognition. A real streaming recogniser (Deepgram adapter in src/realtime/asr.ts, UNTESTED here: no network route) adds its own endpointing and recognition time, typically the largest item in this budget.

## What this does not include

- Real ASR time (see above).
- Browser paint after the WebSocket message: the screen recording (live_demo.webm) shows nudges appearing; its frame timing is not used as a measurement.
- Network between a call platform and this server.
